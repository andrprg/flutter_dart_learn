# Шпаргалка: Prompt Engineering для Cursor

Модуль учит **управлять AI в Cursor**, а не «угадывать код». Задачи в `prompt_engineering_task.dart`: пишешь промпт → получаешь код → оцениваешь → улучшаешь. Теория здесь + вопросы в `interview_questions.md`.

## 1. Хороший промпт для кода

Минимум: **роль + задача + ограничения + формат**.

```
[РОЛЬ]: Senior Flutter-разработчик, Material 3, null safety
[ЗАДАЧА]: StatelessWidget WelcomeCard(userName) — градиент, padding 24, ...
[ОГРАНИЧЕНИЯ]: только Flutter SDK, без пакетов, const где возможно
[ФОРМАТ]: один файл, без пояснений вне кода / или краткий diff
```

Размытое «сделай красивую карточку» vs конкретные размеры, цвета, типы параметров — сравни в задаче 1.

## 2. Базовые техники (фазы 1–2 задач)

| Техника | Суть | Когда |
|---|---|---|
| **Конкретность** | числа, типы, виджеты | всегда |
| **ROLE + TASK + FORMAT** | шаблон структуры | любой фичер |
| **Chain of Thought** | «думай по шагам / сначала план» | сложный layout, баги |
| **Few-shot** | 2 примера → третий в том же стиле | единый UI-kit |
| **Constraints** | «без CustomPainter / без пакетов» | контроль зависимостей |
| **Prompt chaining** | архитектура → UI → логика | экран целиком |
| **Мета-промпт** | «улучши мой промпт» | застрял на формулировке |
| **Debug-шаблон** | проблема / ожидание / repro / код | баги анимаций и state |
| **Code review** | критерии + уровни важности | свой код перед merge |
| **Итерации** | 3 версии промпта с оценкой | полировка UX |
| **Cursor Rules** | `.cursor/rules` как системный стиль | весь проект |

Метрика модуля: подошло **с первой попытки** без доработки — цель, не гарантия.

## 3. Debug и рефакторинг безопасно

Шаблон дебагга (задача 8):

```
[КОНТЕКСТ]: AnimatedCounter
[ПРОБЛЕМА]: ...
[ОЖИДАНИЕ]: ...
[ВОСПРОИЗВЕДЕНИЕ]: ...
[УЖЕ ПРОВЕРИЛ]: ...
[КОД]: ...
```

Рефакторинг (задача 15): сохранить поведение, разбить `build`, вынести валидаторы, показать **diff** и «почему». Не просить «перепиши всё красиво» без тестов/ограничений API.

Оптимизация (задача 14): сначала рабочий код, потом явный список (`const`, кэш картинок, `RepaintBoundary`) + объяснение влияния на FPS.

## 4. Composer, Rules, контекст

- **Composer / Agent** — multi-file (профиль: screen + header + stats + grid). Описывай **каждый файл** и контракты параметров.
- **Rules** — стабильный «системный промпт» проекта: naming, const, ошибки, DO/DON'T.
- **Контекстное окно**: давай релевантные сигнатуры/файлы, не весь репозиторий. Лучше `@` на нужный виджет + тест.

Итерации часто сильнее одного гигантского промпта: шаг → проверить анализатором/тестом → следующий шаг.

## 5. Галлюцинации

Модель может выдумать API пакета или устаревший Riverpod 1.x.

Практика:

- «Опирайся только на присланный код / официальный API Flutter 3.x»
- после генерации — `analyze` / тесты
- для пакетов — уточнить версию из `pubspec.yaml`

## 6. Личный шаблон (задачи 19–20)

```
[РОЛЬ]:
[КОНТЕКСТ ПРОЕКТА]: стек, стиль, что уже есть
[ЗАДАЧА]: поведение + UI
[ОГРАНИЧЕНИЯ]: пакеты, паттерны state, a11y
[ФОРМАТ]: файлы / только патч / тесты
[ПРИМЕРЫ/СТИЛЬ]: few-shot или ссылка на соседний виджет
```

Прогони шаблон на `DashboardScreen` / `PortfolioCard` и зафиксируй топ-3 техники, которые реально сработали у тебя.

## 7. Вопросы с собеса (кратко)

1. Хороший промпт? — роль, контекст, цель, ограничения, формат, примеры.
2. Few vs zero-shot? — примеры задают стиль/формат.
3. CoT? — план по шагам для сложной логики.
4. Безопасный рефакторинг? — поведение, тесты, маленький diff.
5. Контекст? — релевантные файлы, не весь repo.
6. Системный промпт? — Rules / стабильные запреты.
7. Итерации? — чаще лучше одного гиганта.
8. Галлюцинации? — якорь на код + проверка analyzer/docs.
